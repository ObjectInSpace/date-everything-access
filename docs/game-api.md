# Date Everything! - Game API Documentation

## Overview

- Game: `Date Everything!`
- Engine: `Unity 2022.3.28.7056988`
- Runtime: `CLR 4.0.30319.42000`, mod target `net472`
- Architecture: `64-bit`
- Mod loader: `BepInEx 5.4.23.5`
- Primary input stack: `Rewired` with some `Unity InputSystem` layout detection

## Navigation Contracts

- Door post-interaction executor rules are tracked in `docs/door-executor-contract.md`. Use that contract before changing `DoorThresholdAdvance`, `DoorThresholdHandoff`, `DoorPushThrough`, `DoorEntryAdvance`, or source-zone bridge behavior.
- Object-first navigation current contract, as of 2026-05-22: do not treat `CameraSpaces` as walkable geometry. They are camera/runtime labels. Object navigation should route over `navigable_region.bake.json` to the target interactable's reachable interaction band, then react to the game's own interaction readiness state.
- Semantic waypoint contract, as of 2026-05-23: object routes keep the legacy `Waypoints` vector list for sweep/reporting compatibility, but the executor should consume the index-aligned `SemanticWaypoints` list when available. Runtime planner routes now preserve raw baked waypoints and do not inject synthetic `DoorApproach` / `DoorOpening` / `DoorExit` detours. Door names remain segment preconditions only: the executor opens a closed tagged door when needed, then follows the baked route through the doorway. Runtime proof on the bedroom-to-Magnifying-Glass route showed synthetic door portal insertion made the player backtrack into `Doors_Bedroom`; raw route following is the safer contract unless a future proof shows a specific door needs a local doorway micro-route.
- Route install contract, as of 2026-05-23: a failed `SimpleNavPlanner.Plan(...)` must clear any prior `SimpleNavBridge` route and must not start auto-walk. Runtime proof from mixed route tests showed `StartOffBake` / `NoPath` failures could leave an older active route installed, then announce `navigation_autowalk_started` and continue driving stale waypoints. `TryPlanAndInstallSimpleNavRoute()` now returns success, clears the bridge before planning, and callers stop navigation when planning fails.
- Coverage sweep harness contract, as of 2026-05-25: installing a route on `SimpleNavBridge` is not enough to move the player. `SimpleNavCoverageSweep` must start the watcher-owned route autowalk state through `AccessibilityWatcher.TryStartCoverageSweepRoute(...)`, and must stop it through `AccessibilityWatcher.StopCoverageSweepRoute()`. Partial sweep run `artifacts\navigation\sweep\default\sweep_results.json` with `77/77 looped` is therefore a harness-start failure signal, not route-graph proof.
- Offline route validation, as of 2026-05-25: use `uv run python .\scripts\validate_offline_routes.py routes` to validate existing route artifacts, or `uv run python .\scripts\validate_offline_routes.py objects --max-objects N` to plan and validate exported interactables. The validator checks waypoint cells, sampled same-floor segments against `navigable_region.bake.json`, and exported blocker footprint intersections. It also annotates segment failures with CameraSpaces start/end/crossed zones as diagnostics, but CameraSpaces crossings are not failures by themselves. It exits nonzero on failures unless `--warn-only` is passed. Initial proof found both stale sweep artifacts and freshly planned object routes crossing non-navigable cells, so another runtime sweep should wait until planner smoothing uses a conservative supercover-style segment check.
- Door-tagged waypoint tolerance, as of 2026-05-23: raw baked routes may legitimately get close enough to an open door segment while the live door collider blocks shaving the final small remainder. Runtime proof showed bedroom-to-Magnifying-Glass stalled at `waypointDist=1.89` with `Doors_Bedroom` blocking, and gym-bathroom routing stalled at `waypointDist=2.10` with `Doors_Gym_Hall` blocking. Door-tagged route segments therefore use a `2.2m` intermediate waypoint arrival radius while ordinary waypoints remain `1.35m`.
- Smoothing contract, as of 2026-05-23: route smoothing must be stricter than graph connectivity. Runtime proof on the Magnifying Glass route showed the A* route got through doors, then the smoothed leg `wp[24]=(17.39,-0.50,-7.14)` to `wp[25]=(-3.01,-0.50,-25.74)` skimmed the living-room fireplace and timed out with `runtimeBlocker=ankle=Fireplace`. The fireplace is present in the blocker export but rejected as a huge convex hull and represented as wall-like slice segments, so long diagonal visibility checks must sample all touched cells conservatively rather than using a sparse Bresenham line that can miss grazed cells.
- Blocker-classification audit, as of 2026-05-23: `scripts/audit_blocker_classification.py` checks for furniture meshes entering the bake wall-segment path. Current export has 68 wall-segment bake records: 15 walls, 31 door/frame records, 19 exterior fences, 1 thin art frame, and 2 furniture-name matches. ### Object Interaction Readiness

- The base game does not consider "near target" sufficient for interaction. In `BetterPlayerControl.Update()`, it raycasts from `_camera.transform.position - _camera.transform.forward * 0.25f` along `_camera.transform.forward` using `~dateviatorIgnores`.
- The raycast hit transform must directly have `InteractableObj`; then range is checked with `Vector3.Distance(hitInfo.collider.ClosestPointOnBounds(cameraPos), cameraPos) < interactableObj.InteractionRadius`.
- `BetterPlayerControl` publishes the result through `InteractableManager.UpdatePlayerValues(..., inrange)` and `InteractableManager.UpdatePlayerTarget(interactableObj)`.
- Interaction success has multiple layers. Navigation only owns the layers needed to make the input reach the chosen object; it should not own date/dialogue eligibility.
- Layer 1, input targeting: `BetterPlayerControl` must be in `PlayerState.CanControl`, its camera raycast must hit the chosen object's own `InteractableObj` transform, and the camera must be inside that object's `InteractionRadius`. This is the only ordinary-object arrival condition navigation should actively satisfy.
- Layer 2, manager dispatch: `InteractableManager.Interact(...)` additionally requires tutorial permission unless `forceCanInteract` is passed, `GameController.viewState != TALKING`, `_activeObject != null`, and `inrange == true`.
- Layer 3, dialogue/date selection: `GameController.CanSelectObj(...)` / `SelectObj(...)` check Dateviators/glasses, talked-today, charge, realization, and dialogue setup. Navigation should not try to satisfy these for ordinary object routes; the player/game systems own them.
- Layer 4, object effect: alternate interactions run only when `Interactable.CheckCanUse()` succeeds (`noderequired()` visited or empty, and not `stateLock`). Navigation should only care about this layer for route-changing objects such as doors and teleporters.
- `Interactable.CheckCanUse()` is narrow. It returns true only when `noderequired()` is empty or has been visited by Ink, and `stateLock` is false. The only direct call sites found are `GameController.SelectObj(...)` before invoking `AlternateInteractions`, and `InteractableManager.UpdatePlayerTarget(...)` for alternate-interaction prompt display.
- `CheckCanUse()` does not include player/camera targeting, interaction range, locked-door state, door swing collision, `Door.blockInteraction`, or private door `moving` state.
- Normal alternate interaction flow is `BetterPlayerControl` raycast/range -> `InteractableManager.Interact(...)` -> `GameController.SelectObj(...)` -> each alternate `Interactable.CheckCanUse()` -> `Interactable.Interact()` -> `ToggleInteractedWith(...)`.
- `InteractableManager.Interact(...)` only consumes the target when `_activeObject != null`, `inrange == true`, and `GameController.viewState != TALKING`. The `TALKING` check is only a final guard against re-entry; it is not the useful "can initiate a date/dateviator interaction" predicate.
- Dateviator initiation runs through `BetterPlayerControl.HandleChargingUp(...)` and `HandleChargingUpCompleted(...)`: once the held interaction fills and the raycast-selected `hitInteractable` is in range, the game calls `InteractableManager.Interact()`.
- `GameController.CanSelectObj(...)` is not the navigation readiness predicate. It does not check player position, facing, raycast target, or `InteractableManager` range state, and it includes date/charge/realization/talked-today rules that navigation deliberately should not own.
- `InteractableManager.UIon` is also not the navigation readiness predicate. It is prompt/highlight presentation state and is affected by Dateviators equipped state, date status, and alternate-interaction prompt rules.
- Practical mod rule: after route arrival, keep using game state as the authority. The target is interaction-ready only when `Singleton<InteractableManager>.Instance.activeObject` is the chosen `InteractableObj` and `IsPlayerInRange` is true. That expression is the accessible mirror of `BetterPlayerControl`'s private per-frame `flag3` raycast/range result. If it is not true, continue steering camera/body look until the base game selects the object; do not replace the game's interaction model with a separate proximity-only model.
- Door route exception: for traversal, success means the door state actually changes or is already usable. Normal door flow can be blocked by `CheckCanUse()` (`dorian_door`/override node lock and `stateLock`), then `Door.Interact()` can still no-op when private `moving` is true, play only a locked sound when `locked` is true, or fail to open/close when `blockInteraction` or private `collidedWithPlayer` is true. Sliding doors similarly reject while private `moving` or `stateLock` is true, play only a locked sound when `locked`, and can reverse/abort movement when `collidedWithPlayer && stopOnCollision`.
- Door player-blocking checks are runtime-only. `Door.collidedWithPlayer` and `SlidingDoor.collidedWithPlayer` are private fields set by `OnCollisionEnter` / `OnCollisionExit`, and the swing coroutine checks `collidedWithPlayer && stopOnCollision` while moving. This is not usable as an offline route-planning cost, but it is useful and authoritative for runtime execution: read the door state before interacting, keep the player out of the swing volume, and verify `open` / visual rotation after the interaction.
- Current `SimpleNavBridge.TryOpenDoorIfNeeded(...)` already reads part of this state (`Door.moving`, `Door.collidedWithPlayer`, `door.open`, visual rotation) and mirrors the in-range distance check. It does not yet include `CheckCanUse()` / node-lock preflight or public `Door.blockInteraction` / `locked` as explicit skip reasons in the same unified gate.
- Current `SimpleNavPlanner` only partially accounts for door interaction pose. When the target object is itself a `Door`, goal cells are filtered to a hinge-distance band (`DoorHingeBandInnerM=1.5`, `DoorHingeBandOuterM=3.0`) so the player does not stop inside the likely swing arc. When a route merely passes through a door, the planner currently only tags nearby segments with the door name; it does not insert an explicit door-stand waypoint or require the segment to pass through a static door interaction pose.
- Better routing direction: compute static door interaction stand candidates from door metadata (hinge/transform, open type, range, portal/opening where available), reject candidates inside the closed/open swing envelope plus player radius, and add the chosen candidate as an explicit waypoint before the door crossing. Runtime still verifies live fields (`moving`, `blockInteraction`, `locked`, `collidedWithPlayer`) because those cannot be proven offline.
- Preferred architecture is one interaction-readiness model with layered predicates, not a separate door-only interaction system. All interactables share the base object predicate: player can control, game camera raycast selects the chosen `InteractableObj`, and `InteractableManager.IsPlayerInRange` is true. Interactables that have alternate/world effects then add `CheckCanUse()` and type-specific effect predicates. Doors are therefore not special at the input layer; they only add a door-effect layer for route planning and execution.
- Teleporter route exception: success requires `LocationDown` and `LocationUp` to exist and private `inAnimation` to be false; completion should be observed from teleporter state/position change rather than dialogue selection state.
- Current object-first route arrival rule: `AccessibilityWatcher.ApplyAutoWalkSimpleRoute()` may enter the target's XZ interaction-radius disc, but it should only finish once `InteractableManager.activeObject` is the route target and `IsPlayerInRange` is true. While the game has not selected the target, it holds position and writes both yaw (`BetterPlayerControl.look.x`) and pitch (`BetterPlayerControl.look.z`) toward the target so the first-person camera raycast can become authoritative.
- Final targeting aim point, as of 2026-05-23: once the object route reaches the final waypoint, camera aiming should target the route object's collider point nearest the current camera, falling back to the target transform only when no collider is available. Runtime proof near the Magnifying Glass reached the final waypoint and announced nearby objects but never selected the target; aiming at the collider surface is closer to the base game's `ClosestPointOnBounds(cameraPos)` range/raycast model than aiming only at the transform origin. `BetterPlayerControl` consumes `look.x` as body yaw and `look.z` as camera pitch; final-look aiming computes yaw from the player flat forward vector and pitch from the target point in camera-local coordinates.
- Target hierarchy selection, as of 2026-05-23: final object-route completion accepts `InteractableManager.activeObject` when it is the planned object or a parent/child of that planned object. Runtime proof for Magnifying Glass showed the game selecting `MagnifyingGlass_MODEL_UPDATE` while the objective route target was `MagnifyingGlass_Mount_2_MODEL_UPDATE`; this is a valid hierarchy hit and should complete.
- Planning note for large-radius dateables: some ceiling/lamp objects publish the real game default `InteractionRadius = 7.5`. The runtime planner first tries its near-collider/door goal band; if that band has no path, it retries the full interaction-radius disc and lets the first-person readiness check prove selection. This avoids false `no_path` results when a valid standing cell is farther than the conservative 1.5-2.0m target band.

- `SimpleNavPlanner` expects optional `inter_floor_edges` in `navigable_region.bake.json`. `BuildInterFloorEdges()` consumes `stair_ramp` entries as bidirectional ground/upper cell links and `teleporter` entries as virtual-node links.
- `scripts\bake_navigable_region.py` now calls `derive_inter_floor_edges.py` after writing the bake, so future regenerations do not silently drop stair / teleporter edges.
- Current artifact proof on 2026-05-22: the bake contains one `stair_ramp` edge from `===SCENE===/House/Hallway/Stairs` plus one `CrawlspaceLadder` teleporter. A synthetic A* route from the default ground start to the upper stair endpoint succeeds and uses `stairs`, proving the planner can consume the inter-floor edge.
- `upper_hallway_light` proof on 2026-05-22: with the full `7.5m` interaction radius, the target's goal cells include the upper stair component and route planning succeeds with `stairs` + `walk`. With the older 2m cap, goal cells landed only in a different upper-floor component about `1.4m` from the stair component, causing a false `no_path`.
- Static blocker export note: Door and Teleporter connector filtering should apply to descendant collider GameObjects, not only to the exact GameObject with the `Door` / teleporter component. Otherwise child mesh colliders under connector objects can be exported as permanent navigation blockers even though traversal is handled by route execution.

## Runtime Movement Authority

- `BetterPlayerControl` is the player movement authority. It requires both `Rigidbody` and `Collider`; no `CharacterController` movement path was found for the player.
- The accessibility auto-walk does not call a public movement method. It writes the private `BetterPlayerControl.move` and `BetterPlayerControl.look` fields through reflection, then the game consumes those fields in `BetterPlayerControl.FixedUpdate()`.
- In `FixedUpdate()`, when `STATE == CanControl`, the game sets `_rigidbody.isKinematic = false`, zeroes `_rigidbody.velocity`, computes movement from `transform.forward * move.z + transform.right * move.x`, scales it by live movement speed, applies DOTween yaw rotation from `look.x`, and finally assigns `_rigidbody.velocity = Vector3.Lerp(_rigidbody.velocity, targetVelocity, 0.5f)`.
- Grounding is a downward `Physics.Raycast` from `transform.position + Vector3.up * heightdist`; the resulting ground delta becomes the Y component of the velocity. If no ground is hit, Y velocity is forced downward.
- No explicit player `CanMove`, `blocked`, capsule cast, or custom horizontal collision helper was found in `BetterPlayerControl`. Horizontal movement cancellation should therefore be treated as Unity physics collision/contact against the player's collider unless runtime probe data shows the game state/input path is canceling movement first.
- Relevant non-navigation raycasts in `BetterPlayerControl`: camera interactable/dateviator raycast from camera forward using `~dateviatorIgnores`, downward player-floor raycast for floor checks, and an upward raycast used only to decide whether uncrouch is allowed.
- Door and sliding door scripts maintain private `collidedWithPlayer` plus `stopOnCollision` state from collision callbacks. These can affect door animation/interaction behavior, but they are not the player's core movement authority.

## Runtime Movement Probe

- `AccessibilityWatcher` logs `Runtime movement probe ...` on auto-walk loop detector and progress-timeout events.
- The probe casts from the current player position toward the failed movement target using the player collider shape when possible: `CapsuleCastAll` for `CapsuleCollider`, `BoxCastAll` for `BoxCollider`, `SphereCastAll` for `SphereCollider`, and a raycast fallback for other collider shapes.
- The probe ignores the player collider and logs the first non-trigger blocking hit separately from the first trigger hit. Logged blocker fields include object path, collider type, trigger flag, layer, layer name, hit point, distance, and bounds.
- The same line logs command evidence: last auto-walk move/look command, current private `BetterPlayerControl.move`, Rigidbody flat velocity, movement since last command, player state, and `inputAppliedButCancelled`. If `inputAppliedButCancelled=true` and `firstBlockingHit=none`, next investigation should focus on control/state logic instead of collider rasterization.

## Runtime-Proven Mesh Door Blockers

- `scripts\Build-LocalNavigationMaps.ps1` no longer injects authored `AuthoredMeshCollider` AABB blockers into generated local maps. Static generation now remains primitive-collider-only and reports `Counts.AuthoredRuntimeMeshBlockers = 0`.
- Runtime collision occupancy is exported by pressing `Ctrl+Shift+F9`. The existing navmesh diagnostic export now also writes `BepInEx\plugins\local_navigation_maps.physics_sampled.live.json`.
- `LocalNavigationMaps` prefers `local_navigation_maps.physics_sampled.live.json` over `local_navigation_maps.generated.json` on startup, but falls back to the generated static map if the live physics file is missing, malformed, or has no zones. Restart the game after export so the physics-sampled map is loaded.
- Runtime occupancy uses the live `BetterPlayerControl` `CapsuleCollider` dimensions and samples every local-map envelope cell through `Physics.OverlapCapsule` with `QueryTriggerInteraction.Ignore`.
- The export records `BlockedIndices` in the same schema as the generated local maps, plus `BlockedCellDetails` with the first representative blocker object path, collider type, layer, layer name, and bounds for each blocked cell.
- Runtime proof on the first exporter build showed `JsonUtility` wrote top-level counts but omitted the `Zones` array, causing all local planning to fail as `local-maps-unavailable`. The exporter now writes with `DataContractJsonSerializer` and plain `x/y/z` DTOs, and the loader no longer lets an invalid physics file suppress the static fallback map.
- Ground/support colliders whose bounds stay below the player foot band are ignored so ordinary floor contact does not mark every cell blocked. Non-trigger mesh colliders, walls, doors, furniture, and other runtime collision are retained.
- Do not treat broad mesh bounds as local blockers. If physics-sampled occupancy splits a route, fix the target/planner against the sampled connected components instead of adding wider AABB blockers.
- Runtime proof on build `0FD086...` reduced door failures from eight to five and proved the physics map loaded, but exposed a sampling false positive: `upper_hallway` had `0` walkable cells because `Ceilings_UpperHall_1` blocked `451` cells. Ceiling colliders are now ignored during runtime occupancy export, and the export is written atomically through a validated `.tmp` round trip before replacing the live file.
- Runtime proof on build `B5A18...` reduced door failures to three and proved the live map shape was valid: `57` zones, `15441` envelope cells, `3458` blocked cells, and recovered `upper_hallway` walkability. The remaining failures were planner semantics, not exporter false positives: final-entry targets could sit in disconnected physics-sampled components while the executor either preserved the unreachable original goal or fell back to generic `step-source` without door-proxy completion semantics. Current planner policy is to use a reachable source-component proxy when the original post-extended final-entry goal has no local path, and to keep focused Bathroom1 no-source bridge proxies under `door-entry-advance-local` so completing the proxy can release raw final-entry movement.
- Runtime proof on build `5BA154...` showed a second disconnected-goal preservation path: a reachable proxy could be selected, then the forward-progress guard restored the disconnected original goal and caused repeated `NoPath`. Current planner policy is that forward-progress preservation may only restore the original door-entry goal when `LocalNavigationMaps.TryFindPath(...)` proves the original goal is pathable from the live player start; otherwise the reachable source-component proxy must be retained.
- Runtime proof on build `A86E7...` proved the disconnected-original guard works, but exposed two release-path gaps. A focused no-source `door-entry-advance-local` proxy must be releasable by loop detection so the raw final-entry release branch can run after proxy completion. Retained source-zone extended recovery must also be allowed to arm no-progress release from fallback exhaustion, not only from auto-walk loop detection, because a completed extended/final local proxy can otherwise degrade directly into `local-goal-unresolved` fallback failure.

- `Ctrl+Alt+Shift+F9`: start or stop the dev-only transition sweep

### Why these are safe

- No gameplay consumer for `F1` was found in the decompiled game code.
- `Ctrl+F1` reuses the same safe `F1` function key with an added modifier, so it stays outside the game's observed Rewired gameplay bindings.
- `Ctrl+Alt+Shift+F1` stays on the same safe `F1` key family, adds three modifiers, and is explicitly filtered so it does not also trigger help or repeat-last-speech.
- No gameplay consumer for plain `F6` was found in the decompiled game code.
- The plain plus `Ctrl`-modified `F6` bindings stay outside the game's observed Rewired gameplay bindings and do not conflict with the shipped `F2`, `F3`, or `F8` debug keys.
- No gameplay consumer for `F9` was found in the decompiled game code.
- `Ctrl+F9` reuses the same safe `F9` function key with an added modifier, so it stays outside the game's observed Rewired gameplay bindings.
- `Ctrl+Shift+F9` reuses the same safe `F9` function key with one more modifier and is explicitly filtered in the hotkey handler so it does not also trigger plain debug toggle or the settings menu.
- `Ctrl+Alt+Shift+F9` stays on the same safe `F9` key family, adds a third modifier, and is explicitly filtered so it does not also trigger debug, settings, or navmesh export.
- They sit outside the Rewired action flow the game relies on for normal keyboard/controller input.

### Keys to avoid

- `F2`, `F3`, `F8`: explicitly used by shipped debug/editor-style code
- `Confirm`, `Cancel`, arrows, number keys, and face-button-equivalent actions: already part of live UI/dialogue flows
- `F12`: runtime observation on this machine showed Steam screenshot interception even though the game code did not claim it

- Tutorial objective resolution can surface a model-child `InteractableObj` instead of the usable root interactable, especially for Maggie and other multi-part dateables. Tracker resolution should canonicalize within the interactable hierarchy before trusting the candidate for zone lookup or navigation.
- `UpdateNavigationState()` should not rebuild the navigation path every poll while the player is still in the current step's `FromZone`. Rebuilding every frame causes repeated tracker restarts and unstable open-passage auto-walk behavior even when the target step has not changed.
- Runtime transit zones such as `stairsdown` can be outside the authored navigation graph. Auto-walk must keep the current graph step alive through those zones and continue toward the step's destination graph zone instead of refreshing the path immediately on entry-waypoint arrival.
